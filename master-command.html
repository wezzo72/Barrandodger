Master Build Command — Genesis

This page publishes the instruction set that constrained the construction of this presentation website. It is reproduced for methodological transparency: so readers can see what the builder was told to do, and what it was forbidden to do.

This page is not evidence against any person or organisation. The Master Build Command is a software and archival specification. It does not establish that any allegation is true. It requires the opposite discipline: never silently convert allegation, inference or interpretation into fact.

How this site was made

  1. The owner opened a public GitHub issue titled GITHUB FORENSIC ARCHIVE — MASTER BUILD COMMAND V1 on the primary archive repository.
  2. The command assigned the builder the role of impartial senior software architect, forensic information architect, digital archivist, research-methodology designer, accessibility specialist, SEO engineer and academic publishing systems developer.
  3. The command required a searchable, navigable, evidence-based digital archive — and simultaneously required strict separation of documentary status labels.
  4. Build progress is recorded in BUILD_STATUS.md. Work proceeds phase by phase. Completed architecture is not rebuilt from zero without instruction.
  5. This presentation layer (wezzo72/Barrandodger) does not replace or rewrite the primary evidence stores.

ROLE (as stated in the command)

Act as an impartial senior software architect, forensic information architect, digital archivist, research-methodology designer, accessibility specialist, SEO engineer and academic publishing systems developer.

Build a complete, professional, publicly accessible digital archive and research website for:

Dr Richard William McLean / Barran Dodger

The website must transform the existing GitHub repository and its documentary corpus into a searchable, navigable, evidence-based digital archive, research library, forensic evidence centre, digital museum, publication platform and public-interest documentation portal.

Required evidentiary distinctions

The system must be designed so that a reader can independently inspect the underlying documents and distinguish:

  • DOCUMENTED FACT
  • PRIMARY-SOURCE RECORD
  • OFFICIAL RECORD
  • JUDICIAL FINDING
  • OFFICIAL DETERMINATION
  • CORROBORATED MATERIAL
  • AUTHOR’S ACCOUNT
  • ALLEGATION
  • INFERENCE
  • INTERPRETATION
  • POSSIBLE LEGAL CHARACTERISATION
  • UNVERIFIED MATERIAL
  • DISPUTED MATERIAL
  • RESEARCH QUESTION

Never silently convert an allegation, inference or interpretation into a fact.

2. First priority — protect the existing evidence

Archival principle stated in the command:

ORIGINAL EVIDENCE MUST REMAIN PRESERVED; WEBSITE PRESENTATION MAY CHANGE, BUT THE UNDERLYING RECORD MUST NOT BE ALTERED.

  • DO NOT delete existing evidence.
  • DO NOT rename evidence files merely for aesthetic reasons.
  • DO NOT overwrite original evidence.
  • DO NOT modify the contents of primary-source documents.
  • If restructuring is necessary, preserve the original path/reference in metadata.

3. Build status system

Create /spec/BUILD_STATUS.md. At the beginning of every build session: read it, inspect the project, continue from the existing state, never rebuild completed architecture unnecessarily. After every meaningful build: update completed work, files created/modified, unresolved errors, next recommended phase.

Never restart the project from zero unless explicitly instructed.

Legal / defamation safeguards (command text)

Every potentially accusatory page must contain an evidence-status system.

Do not state: “X committed a crime” unless supported by an authoritative finding.

Prefer wording such as:

  • “The archive contains an allegation that…”
  • “The documents record…”
  • “The available material appears consistent with…”
  • “The evidence raises a question whether…”
  • “No judicial finding has been identified in the material reviewed.”
  • “The allegation is disputed.”
  • “The matter remains unresolved.”
  • “Further independent investigation would be required.”

This is a research archive, not a court.

No fabrication rule (absolute)

ABSOLUTELY DO NOT INVENT: documents, people, events, quotes, laws, legal findings, court decisions, government findings, awards, academic publications, statistics, financial figures, corroboration, citations, sources, URLs, testimony, institutional motives, criminal conduct, causal relationships.

If information cannot be established from the repository or a verified external source, label it: UNKNOWN · UNVERIFIED · CLAIMED · REQUIRES SOURCE.

Source hierarchy required by the command

  1. LEVEL 1 — JUDICIAL / OFFICIAL DETERMINATION
  2. LEVEL 2 — PRIMARY GOVERNMENT RECORD
  3. LEVEL 3 — CONTEMPORANEOUS PRIMARY DOCUMENT
  4. LEVEL 4 — INDEPENDENT CORROBORATION
  5. LEVEL 5 — AUTHOR’S DOCUMENTED ACCOUNT
  6. LEVEL 6 — SECONDARY SOURCE
  7. LEVEL 7 — INTERPRETATION
  8. LEVEL 8 — SPECULATION / UNVERIFIED CLAIM

The interface must make this distinction visible.

Public research disclaimer (command text)

This archive presents documentary material for public research, historical documentation and independent scrutiny. Inclusion of a person, organisation, allegation, event or legal concept does not by itself establish wrongdoing or legal liability. Evidentiary status is identified wherever practicable, and readers are encouraged to inspect the underlying primary materials, consider counter-evidence and distinguish documented facts from allegations, inference and interpretation.

Initial build priority (command text)

DO NOT attempt to build every feature in one operation. FIRST BUILD ONLY: inspect repository, preserve existing archive, create architecture, specifications, data schemas, BUILD_STATUS, design system, navigation, homepage shell, evidence-status components, document/article/card components, basic search framework, GitHub Pages deployment, archive inventory, tests, fix errors, update BUILD_STATUS — then STOP. Do not proceed to all forensic modules during the first build.

Subsequent work continues only when instructed: CONTINUE FROM BUILD STATUS. Execute Phase N only.

Why this command is published here

  • Impartiality of construction — the constraints were written before the pages; the builder is bound by them.
  • Genesis — readers can see that the site is the product of an explicit archival specification, not an ad-hoc narrative website.
  • Auditability — if a page appears to overclaim, the command itself is the standard against which to check it.
  • Phase discipline — BUILD_STATUS records what has and has not been implemented.
