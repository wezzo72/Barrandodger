Forensic Integrity Protocol

Robust verification framework for factual reliability, intellectual clarity, and legal fortification of the entire archive.

NOT A FINDING. NOT A VERDICT. NOT LEGAL ADVICE.
This protocol provides tools and language for independent examination. It does not establish that any allegation is true. A link, a hash, or a timestamp is not a finding. Readers must examine primary sources.

1. Cryptographic Integrity Verification

SHA-256 Hash Verification

  1. Download the source PDF or file from the GitHub repository (wezzo72/Barrandodger or linked mirrors).
  2. Compute the SHA-256 hash locally using standard tools (e.g., shasum -a 256 filename.pdf on macOS/Linux, or certutil on Windows).
  3. Compare against the published hash on the corresponding page or stamp.
  4. Match confirms the file bytes have not been altered since the hash was recorded.

OpenTimestamps (Bitcoin Calendar)

Where .ots receipts exist, they provide a cryptographic proof that the file (or its hash) existed at or before a certain time, anchored to the Bitcoin blockchain via public calendars. Pending block confirmation does not invalidate the calendar submission. Independent verification tools for OpenTimestamps are publicly available.

Git History and Provenance

Every commit on GitHub provides an immutable (to the extent of the platform's integrity) record of when content was added or modified, by whom, and the exact blob SHA. This serves as a digital chain-of-custody analogue.

2. Evidence Classification and Probability Language

To enhance factual precision and avoid converting allegation into fact:

  • A – Documented existence: The file or record exists; quoted text appears in the opening pages or as named. This is verifiable by inspection.
  • B – Incomplete or partial: Further pages, context, or related records needed for fuller assessment.
  • C – Corroboration needed: Consistent with other records but requires independent cross-check.
  • D – Narrative / allegation / interpretation: Author’s account or framing. Not established as fact by the document alone.
  • H – High-consequence claim: Do not treat as established without strong, multi-source corroboration.

Probability and weight language (use precisely):

  • “The record is consistent with…” (supports but does not prove)
  • “Does not contradict…”
  • “Requires independent verification of…”
  • “The existence of the correspondence is established; the accuracy of any underlying allegation is not established by this entry alone.”
  • Avoid absolute terms such as “undeniable,” “proven,” or “certain” for unadjudicated claims.

This language increases intellectual rigor and legal defensibility by matching the strength of the claim to the strength of the evidence.

3. Chain-of-Custody Equivalent for Digital Archives

  1. Source acquisition (original agency letterhead, FOI release, personal correspondence as provided).
  2. Hash computation and publication.
  3. Timestamping (OpenTimestamps or Git commit date).
  4. Multiple mirrors (GitHub Pages, Backup repo, other repositories).
  5. Public availability for independent re-hashing.

Any break in this chain (e.g., unpublished intermediate versions) should be noted. Preservation of originals is preferred.

4. Legal and Intellectual Fortification Notes

Not legal advice. For orientation only. Consult qualified professionals for any formal proceeding.
  • Australian evidence principles for documents (authenticity, relevance, hearsay exceptions for business/government records) can be considered by examiners.
  • Human rights instruments (ICCPR, CRPD, etc.) are referenced as standards, not as established findings of breach.
  • FOI and administrative law records demonstrate institutional awareness or decisions; sequence is not automatically causation.
  • Theological or prophetic writings are author’s interpretation and remain so labeled.

5. Independent Verification Checklist

  • ☐ Locate the primary file on GitHub.
  • ☐ Verify SHA-256.
  • ☐ Check OpenTimestamps receipt if available.
  • ☐ Review Git commit history for addition date.
  • ☐ Read the full document, not extracts only.
  • ☐ Classify using A/B/C/D/H.
  • ☐ Cross-reference related records.
  • ☐ Distinguish documented fact from allegation or interpretation.
  • ☐ Note any limitations (partial text extraction, pending timestamps, etc.).

6. Completeness and Verification Status of the Archive

The archive is a living finding aid. Completeness is relative to the materials made public by the owner. Verification status of any individual entry is as labeled. Readers are invited to contribute corrections or additional public-source references via the contact methods on the main site, with the same classification standards applied.
